## Introduction

This is the specification for the `persist.redis` library of the [Ballerina language](https://ballerina.io/), which provides Redis datastore support for the persist client that the persist tool generates. It covers what is specific to Redis: the supported types, the configuration of the generated client, how records are stored in Redis, and how the client behaves. The data model, the derived entity types, the generated client API and the error types are specified in the [persist specification](https://github.com/ballerina-platform/module-ballerina-persist/blob/main/docs/spec/spec.md), which this specification builds on.

The conforming implementation of the specification is released and included in the distribution. Any deviation from the specification is considered a bug. The released versions of the specification can be found under the relevant GitHub tag.

### Notation

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY and OPTIONAL are interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174) when, and only when, they appear in all capitals. Sentences that state behaviour in the present tense are also normative. The overview, notes and examples are informative.

## 1. Overview

The `persist.redis` library lets the persist client generated by the [persist tool](https://github.com/ballerina-platform/persist-tools/blob/main/docs/spec/spec.md) store the records of a data model in a Redis database. The datastore is selected with the `redis` datastore name, for example with `bal persist add --datastore redis` or `bal persist generate --datastore redis`. The persist tool then generates a client that uses this library, a configuration file with the connection configurables, and a platform dependency on the native library with the group ID `io.ballerina.lib` and the artifact ID `persist.redis-native`.

Each record is stored as a Redis hash, and each relation is tracked with Redis sets. Field values are stored as strings and converted back to their Ballerina types when they are read. The client can set an expiry on the keys it writes and reads, so that Redis can be used as a cache.

The Redis datastore is experimental. `bal persist generate` prints a warning that the support for the Redis data store is an experimental feature, and that its behaviour may change in future releases.

The public types and functions of the library are used by the generated client. An application uses the generated client, as specified in the [persist specification](https://github.com/ballerina-platform/module-ballerina-persist/blob/main/docs/spec/spec.md#4-derived-entity-types-and-persist-clients).

## 2. Terminology

The terms entity, identity field, relation field, owner, derived entity types and persist client are used as defined in the [persist specification](https://github.com/ballerina-platform/module-ballerina-persist/blob/main/docs/spec/spec.md#2-terminology). In addition:

- **Redis client:** the persist client generated for the `redis` datastore.
- **Key suffix:** the string formed by joining the values of the identity fields of a record, in the declaration order of the identity fields, with `:`. Each value is written as its string form.
- **Record key:** the Redis key of the hash that stores a record, as specified in [5.2](#52-records).
- **Association set:** a Redis set that holds the key suffixes of the owner records that refer to one record of the other entity of a relation, as specified in [5.4](#54-association-sets).
- **Key expiry:** the time to live that the Redis client sets on the keys it writes and reads when `maxAge` is greater than `0`, as specified in [6.6](#66-key-expiry).

## 3. Supported types

### 3.1. Description

The types that the fields of an entity can have with the Redis datastore. The data model is defined as specified in [data model definition](https://github.com/ballerina-platform/module-ballerina-persist/blob/main/docs/spec/spec.md#3-data-model-definition) of the persist specification.

### 3.2. Simple types

1. The simple types of the Redis datastore are `int`, `boolean`, `decimal`, `float`, `string`, enum types, `time:Date`, `time:TimeOfDay`, `time:Utc` and `time:Civil`.
2. No array type is supported, including `byte[]`.
3. An identity field has one of the types that the persist specification allows for identity fields with every datastore.

### 3.3. Optional and nillable fields

Let `T` be a simple type that does not contain `()`.

| Field definition | Allowed | Semantics |
|---|---|---|
| `T field` | Yes | The record always has a value for the field. |
| `T field?` | Yes, except on an identity field | The record may have no value for the field. A field with no value is not stored, as specified in [5.2](#52-records). |
| `T? field` | No | - |
| `T? field?` | No | - |

The rules for nillable fields apply to fields of a simple type. The `EntityType?` relation field of a one-to-one relation is allowed.

### 3.4. SQL annotations

1. The `keys` of the `@sql:Relation` annotation name the foreign key fields of the owner, as specified in the persist specification.
2. The other annotations of the `ballerinax/persist.sql` package have no effect on the Redis client. In particular, `@sql:Name` does not change the record key or the hash field names, `@sql:Index` and `@sql:UniqueIndex` do not create an index or enforce uniqueness, and `@sql:Generated` does not remove the field from the insert type, so the application provides its value.

### 3.5. Compile-time validation

When the `Ballerina.toml` file of the package configures the `redis` datastore for the model, the `persist` compiler plugin reports these conditions as errors, in addition to the conditions that apply to every datastore:

| Condition | Code |
|---|---|
| A field's type is not a simple type of the Redis datastore | `PERSIST_305` |
| A field's type is an array type | `PERSIST_306` |
| A field of a simple type is nillable, `T? field` or `T? field?` | `PERSIST_308` |
| An identity field is optional, `readonly T field?` | `PERSIST_309` |

The plugin does not report `PERSIST_304` for an optional field with the Redis datastore.

## 4. Configuration

### 4.1. Description

The configurables that the generated Redis client reads to connect to Redis and to set the key expiry.

### 4.2. Configuration

The persist tool declares these configurables in the module that holds the generated client. Both are required, and are set in `Config.toml` under the `<package>.<module>` table of that module.

| Configurable | Type | Default | Meaning |
|---|---|---|---|
| `connectionConfig` | `redis:ConnectionConfig` | Required | The connection configuration of the [`ballerinax/redis`](https://central.ballerina.io/ballerinax/redis/latest) client that the Redis client connects with, such as the connection URI or the host, port and credentials. The persist tool writes `connection = "redis://localhost:6379"` in the generated `Config.toml`. |
| `cacheConfig.maxAge` | `int` | Required | The key expiry in seconds. A value greater than `0` enables the key expiry, as specified in [6.6](#66-key-expiry). `0` or a negative value disables it, so keys do not expire. The persist tool writes `-1` in the generated `Config.toml`. |

For example, the `Config.toml` of a package `shop` with the generated client in the module `shop.store`:

```toml
[shop.store.connectionConfig]
connection = "redis://localhost:6379"

[shop.store.cacheConfig]
maxAge = -1
```

### 4.3. Behaviour

1. The `init` function of the Redis client creates one `redis:Client` with `connectionConfig`, and uses it for all entities. When the `redis:Client` cannot be created, `init` returns a `persist:Error` with the message of the error.
2. The `close` function closes the `redis:Client`. When closing fails, it returns a `persist:Error` with the message of the error.
3. The same `maxAge` applies to every entity of the client.

## 5. Storage layout

### 5.1. Description

How the records and relations of a data model are stored as Redis keys.

### 5.2. Records

1. Each record is stored as a Redis hash. Its record key is `<entity>:<key suffix>`, where `<entity>` is the entity name as declared in the model, with the case preserved. For example, the `Employee` record with the identity `1` has the record key `Employee:1`, and a record of an entity with the identity fields `code` and `year` has a record key such as `Course:CS101:2024`.
2. The `:` in a value of an identity field is not escaped.
3. The record key does not include the package or module name. Two models that have an entity with the same name and use the same Redis database share the same record keys.
4. The hash has one hash field for each field of the entity type of the record, including the foreign key fields of the owner. The hash field name is the field name, without a leading `'`.
5. An optional field with no value has no hash field.
6. The Redis client does not create any key for an entity other than the record keys and the association sets. The `get` resource method finds the records of an entity by their record keys, as specified in [6.2](#62-retrieving-records).

### 5.3. Field values

1. Each field value is stored as a string, and is converted back to the field type when it is read.
2. An `int`, `float`, `decimal` or `boolean` value is stored as its string form, and is read with `int:fromString`, `float:fromString`, `decimal:fromString` or `boolean:fromString`. A `string` value is stored as is. An enum value is stored as the string value of the enum member.
3. A value of a `time` type is stored in these formats:

    | Type | Format | Example |
    |---|---|---|
    | `time:Date` | `<day>-<month>-<year>`, without zero padding | `5-3-2024` |
    | `time:TimeOfDay` | `<hour>:<minute>:<second>`, without zero padding | `9:30:0` |
    | `time:Utc` | The string that `time:utcToString` returns | `2024-03-05T09:30:00Z` |
    | `time:Civil` | `<year>-<MM>-<DD>T<hh>:<mm>`, followed by `:<ss>` when `second` is present, by the UTC offset as `+hh:mm:ss` or `-hh:mm:ss` when `utcOffset` is present, and by `(<timeAbbrev>)` when `timeAbbrev` is present | `2024-03-05T09:30:00+05:30:00` |

4. When a stored value cannot be converted to the field type, the operation that reads it returns a `persist:Error` with the message of the conversion error.

### 5.4. Association sets

1. For each relation, the Redis client keeps one association set for each record of the entity that is not the owner. The key of the association set is `<record key>:<relation field>`, where `<record key>` is the record key of that record, and `<relation field>` is the name of the relation field of that entity.
2. The association set holds the key suffix of each owner record whose foreign key refers to the record.
3. An association set exists only while it has members, as a Redis set does.

#### 5.4.1. Example: Keys of a data model

For the `Building`, `Workspace` and `Employee` entities of the [derived entity types example](https://github.com/ballerina-platform/module-ballerina-persist/blob/main/docs/spec/spec.md#42-derived-entity-types) of the persist specification, the building `B1`, the workspace `W1` in `B1`, and the employee `1` in `W1` are stored in these keys:

| Key | Type | Content |
|---|---|---|
| `Building:B1` | Hash | `buildingCode` = `B1`, `city` = `Colombo` |
| `Workspace:W1` | Hash | `workspaceId` = `W1`, `workspaceType` = `Desk`, `locationBuildingCode` = `B1` |
| `Employee:1` | Hash | `empNo` = `1`, `name` = `Jane`, `workspaceWorkspaceId` = `W1` |
| `Building:B1:workspaces` | Set | `W1` |
| `Workspace:W1:employees` | Set | `1` |

## 6. The Redis client

### 6.1. Description

The behaviour of the resource methods of the Redis client. The resource methods, their inputs and their results are specified in [persist clients](https://github.com/ballerina-platform/module-ballerina-persist/blob/main/docs/spec/spec.md#43-persist-clients) of the persist specification. The Redis client does not have the native SQL methods.

### 6.2. Retrieving records

1. The `get` resource method reads every key that matches `<entity>:*`, and keeps the keys whose Redis type is hash, which are the record keys of the entity. It reads the non-relation fields of all these records when it is called, and returns them as a stream. Filtering, ordering and limiting are not done in Redis: a query expression on the stream applies them in the application.
2. The order of the records in the stream is unspecified.
3. The `get` by identity resource method reads the record with the record key formed from the given identity values. When the record does not exist, it returns a `persist:NotFoundError`.
4. Both methods read only the non-relation fields of the target type, and the identity fields. An identity field that the target type does not have is not included in the result. An optional field that the record has no value for is not included in the result.
5. For each relation field of the target type, the client reads the related records as follows. `get` does this for each record as the stream advances.
    1. When the record is the owner of the relation, the related record is the record whose record key is formed from the foreign key fields of the record. When that record does not exist, the method returns a `persist:NotFoundError` for the key of the related record.
    2. Otherwise, the related records are the records whose key suffixes are the members of the association set of the record. A member whose record does not exist is removed from the association set, and is not included in the result.
    3. A relation field of an array type holds the related records, and the empty array `[]` when there are none. A relation field of a record type holds the related record, and the empty record `{}` when there is none.
6. The client reads only the fields of the related records that the target type has.

### 6.3. Inserting records

The `post` resource method inserts the given records as follows:

1. The client forms the record key of each given record. When a record with any of these keys exists, it returns a `persist:AlreadyExistsError`, and inserts no record.
2. Otherwise, it processes the given records in order. For each record:
    1. For each relation that the entity owns, when the relation is one-to-one and the association set of the referenced record has a member, the client returns a `persist:ConstraintViolationError`.
    2. The client adds the key suffix of the record to the association set of the referenced record. When the referenced record does not exist, it returns a `persist:ConstraintViolationError`.
    3. The client writes the fields of the record to its hash.
3. When the client returns an error at step 2, the records processed before the failing record remain inserted.

### 6.4. Updating records

The `put` resource method updates the record with the given identity as follows:

1. When the record does not exist, the client returns a `persist:NotFoundError`.
2. For each relation that the entity owns and whose foreign key fields the update changes, the client checks the newly referenced record. When it does not exist, the client returns a `persist:ConstraintViolationError`. When the relation is one-to-one and the association set of the newly referenced record has a member, the client returns a `persist:ConstraintViolationError`.
3. The client writes each field of the update to the hash of the record. A field that the update does not have keeps its value, so an optional field that has a value cannot be removed.
4. For each relation whose foreign key fields the update changed, the client adds the key suffix of the record to the association set of the newly referenced record, and removes it from the association set of the previously referenced record.
5. The client reads the updated record back and returns it.

### 6.5. Deleting records

The `delete` resource method deletes the record with the given identity as follows:

1. The client reads the record. When the record does not exist, it returns a `persist:NotFoundError`.
2. For each relation that the entity owns, the client removes the key suffix of the record from the association set of the referenced record.
3. The client deletes the hash of the record, and returns the record as it was read at step 1.
4. The client does not check whether other records refer to the record. Their foreign key fields keep their values, so reading such a record with the relation field returns a `persist:NotFoundError`, as specified in [6.2](#62-retrieving-records).

### 6.6. Key expiry

When `maxAge` is greater than `0`:

1. Each time the client writes or reads a record, including a related record, it sets the expiry of the record key to `maxAge` seconds.
2. Each time the client writes or reads an association set, it sets the expiry of the association set to `maxAge` seconds.
3. A key that has expired does not exist, so a record whose record key has expired is treated as a record that does not exist.
4. When the client cannot set the expiry of a key because the key does not exist, the operation returns a `persist:NotFoundError`.

### 6.7. Errors

1. The resource methods return the error types defined in the persist specification. The Redis client returns them in these conditions:

    | Resource method | Error | Condition |
    |---|---|---|
    | `get` | `persist:NotFoundError` | A record of the stream owns a relation whose referenced record does not exist, and the target type has that relation field. The stream returns the error. |
    | `get` by identity | `persist:NotFoundError` | No record has the identity, or the record owns a relation whose referenced record does not exist and the target type has that relation field. |
    | `post` | `persist:AlreadyExistsError` | A record with the identity of a given record exists. |
    | `post` | `persist:ConstraintViolationError` | A foreign key refers to no record, or refers to a record of a one-to-one relation that another record already refers to. |
    | `put` | `persist:NotFoundError` | No record has the identity. |
    | `put` | `persist:ConstraintViolationError` | A changed foreign key refers to no record, or refers to a record of a one-to-one relation that another record already refers to. |
    | `put` | `persist:ReadBackError` | The record is updated, but cannot be read back for a reason other than a `persist:NotFoundError`. |
    | `delete` | `persist:NotFoundError` | No record has the identity. |

2. The error messages are as follows, where `<entity>` is the entity name, `<key>` is the record key, `<n>` is the number of given records whose record key exists, and `<referenced entity>` is the name of the entity the foreign key refers to:

    | Error | Message |
    |---|---|
    | `persist:NotFoundError` | `A record with the key '<key>' does not exist for the entity '<entity>'.` |
    | `persist:AlreadyExistsError` | `Record(s) already exist with the same key for the entity '<entity>'. Number of keys exists : <n>` |
    | `persist:ConstraintViolationError` | `An association constraint failed between entities '<entity>' and '<referenced entity>'` |

    For example, `get` by identity for the missing `Employee` record `5` returns a `persist:NotFoundError` with the message `A record with the key 'Employee:5' does not exist for the entity 'Employee'.`.

3. Any other failure, including a failure of a Redis command, is returned as a `persist:Error` with the message of the underlying error. The `get` resource method returns such an error from the stream.

## 7. Transactions

The Redis client does not support transactions.

1. The resource methods do not take part in a Ballerina `transaction` statement. Their changes take effect when each Redis command runs, and are not undone when the transaction fails.
2. A `post`, `put` or `delete` runs several Redis commands, which are not atomic and are not isolated from other clients of the same Redis database. When one of them fails, the changes of the commands that ran before it remain.

## 8. Security considerations

1. The `connectionConfig` configurable holds the Redis connection URI or parameters, which can contain the user name and password of the Redis database. These values are read from `Config.toml` or the other configuration sources of the program. The transport security of the connection is the one configured in `connectionConfig`, as specified by the `ballerinax/redis` library.
2. The Redis client logs each Redis command that it runs at the `DEBUG` log level. The log of an insert includes all field values of the inserted record, and the log of an update includes the new field values, so field values are written to the log when the `DEBUG` level is enabled for the module.
3. The Redis client does not restrict access to the keys of a data model. Any client that can connect to the Redis database can read and change the records and association sets, and changes made outside the Redis client are not validated.
4. The `get` resource method uses the Redis `KEYS` command, which scans every key of the Redis database.
